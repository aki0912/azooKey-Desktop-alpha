2026-09-24。HEAD `362fa25b9dc66f5df4e096ced74bffda1747d2db`。調査対象は700原文の現行モデルと930原文の再学習候補。製品コード・閾値・導入済みIMEは変更していない。人工入力だけを使用し、利用者の本文・確定文脈を取得していない。

## 結論

再学習によるスコア分布の変化に、**入力途中を評価しないモデル選定**と、**日英の判定スコアを漢字変換範囲にも使う表示処理**が重なった。文字コードやexportの不一致ではない。特に、英語境界をモデルが提案しないと辞書照合できないことと、日本語の採用条件を厳しくすると逆に全文を漢字変換する場合があることが、退行を増幅している。

一方、12 assertion失敗が12個の利用者向け不具合を意味するわけではない。`asitan` は下位adapterでは失敗するが、日本語優先の現行runtime構成では「明日n」を保つ。`asitano` も変換範囲は変わるが表示は同じ。さらに実Zenzaiでは `asitanote` と `made` の表記も維持された。前回の実装記録の退行は、利用者に見える変化・通常辞書だけの変化・内部の契約違反を区別して読む必要がある。

## 入力ごとの直接原因

以下の数値は特記しない限り文脈取得不可。pJAは文字の校正後スコアで、単語・変換候補の正解確率ではない。

### `asitan`：末尾の全位置条件に届かない

末尾nのpJAが0.860961→0.553882へ低下した。`TrainedMixedSegmenter.admitsPendingTail` は全位置0.65以上を要求するため、下位adapterは全体をunresolvedにする。新モデルの採用閾値だけを旧値に戻しても失敗は残る。

ただし、runtimeの `JapanesePreferredSegmenter` は全体の平均0.917378で日本語へ戻し、既存parserで完成prefix＋nを変換する。通常辞書で「明日n」を確認した。既存テストのうち下位adapterを直接使う経路の契約違反であり、自動モードの表示が必ず崩れるとはいえない。

### `asitano`：閾値上昇による内部区間の変化

平均0.987513は旧0.98を満たすが新0.99に届かない。新モデルでは `asita` の漢字変換＋`no` の読み表示に分かれる。閾値だけを旧値に戻すと一つのjapaneseRomanへ戻る。通常辞書の表示は両方「明日の」であり、ここも表示文字列と変換区間の回帰を区別する。

### `asitanote`：信頼が下がると全文の漢字変換へ進む逆転

現行モデルは `asitano` と `te` を分け、「明日のて」とする。候補では末尾t/eが約0.5881/0.7024から0.3192/0.4881へ下がり、ViterbiがteをRAWにする。前半も採用閾値に届かず、下位adapterに採用済みの日本語区間が残らない。

日本語優先処理はteを英単語として採用できず、全体の平均0.838297がhold0.65以上なので全文をjapaneseRomanへ戻す。結果、通常辞書では「明日の手」になる。`JapanesePreferredSegmenter.segment` の採用済み区間を維持する処理と、`japaneseSpan` の全体平均による変換が原因である。

実Zenzaiは全文変換でも「明日のて」を返したため、この人工例の最終表記は維持された。変換区間の変化と表記の変化は同一ではない。

これは係数だけの問題ではない。**旧係数のまま採用閾値だけ0.99へ上げた対照でも「明日の手」になった**。採用を厳しくして前半の区間が消えると、後段がかえって広い変換範囲を作る。逆に、この閾値対照だけで旧モデルの句点例も全文変換へ進んだ。閾値を句点例に合わせて操作すると別の入力途中を壊す構造になっている。

### `made`：日英のスコアを漢字／かな選択に流用

平均pJAは0.632511→0.809208。どちらも最終的には日本語だが、hold0.65を跨いでjapaneseKanaからjapaneseRomanへ変わる。通常辞書では「まで」→「間で」。閾値だけを旧値に戻しても変わらない。

実ZenzaiはjapaneseRomanでも「まで」を返し、最終表記は維持した。

LRの教師ラベルはJA_ROMAN／RAWであり、「まで」と読むか「間で」と漢字変換するかを学習していない。日本語らしさをそのまま漢字候補へ進む条件に使うため、言語判定が日本語へ強まること自体が表示の退行になる。個別語の無条件保留を追加する根拠にはしない。

### `asitahameetingg`：英語の末尾境界が消え、辞書照合の候補から外れる

最後のgのpJAは0.548635→0.273869。切替ペナルティ0のため、旧 `[7,14)` meeting＋`[14,15)` gが、新 `[7,15)` meetinggという一つのRAW runになる。

`embeddedEnglishSplit` が調べるのはRAW runの開始・終了を組み合わせた範囲だけ。新しい経路ではmeetinggを調べるが、辞書にあるmeetingの末尾14は候補にならない。英語区間自体の証拠が弱まったのではなく、**後続のgをもっと英語らしいと判定したため、既知の英単語まで失う**。日本語優先の全体読みへ戻り、通常辞書構成では「あしたはめえちngg」となる。さらにaまで打つと境界が戻り、meetingを再び保持する。

閾値／校正の旧値復元では解消しなかった。逐次入力でも過去の英語保持は候補境界がないため適用できない。表示の直前値を固定する対応では、全体入力と一致する解決にならない。

### 空文脈の `note`：旧モデルの過大な日本語加点が消えた

取得成功の空文脈が、取得不可より加えるlogitは旧+7.882789、新+0.282207。空文脈でのnoteの平均pJAは0.999442→0.519556となり、辞書と既存の英語採用条件を満たしてrawになる。人工の「明日」「これは」という非空文脈では日本語のまま。

この失敗は「文脈を使えなくなった」ことを意味しない。旧trainの空文脈にはJA／RAWの学習対象がなく、今回その偏りが減った影響である。旧テストは空文脈でも日本語という期待を持つが、空文字だけでは入力意図を識別できない。取得成功空と取得不可で意味のない大差を付けない方針と、曖昧語の表示方針を先に明文化する必要がある。今回テストの期待値は変更していない。

## 学習側で変わったこと

### 完成文の増強が既存prefixの比率を下げた

`learning.matrix` は、原文に属する全派生行の学習対象文字位置へ重み1を均等分配する。原文ごとの総重みは保持されるが、用途別の配分は保持されない。

旧trainの同じ481原文だけで比較すると、入力途中prefixの重み合計は241.0788→146.5375（約39.2%減）、原文そのものは140.4711→92.7839。代わりに完成した記号variantへ83.3155、文脈variantへ106.3415が移った。prefix行は1,959→1,933で、件数よりも重みが大きく減る。26行の減少は新しいsplit間衝突の除外による。

`dataset.build_dataset` は元文・ローマ字variantから最大8prefixを作るが、追加した記号／文脈variantからprefixを作らない。したがって、文脈なし／空の対照を完成文へ追加しても、その対照の入力途中は揃わない。

### モデル選定が最終表示を評価していない

`learning.train` はdev原文だけのlog loss、校正はcalibration原文だけ、閾値選択もdev原文だけのLR＋Viterbi＋保留を使う。入力途中、英単語辞書、日本語優先、漢字／かなの区間は選定対象にない。

候補モデルへ旧閾値を適用すると、新dev155英語span中、新規文 `saishonibackup,tsuginikoushinnwookonaimasu.` のbackupの一部がJAになり、英語破壊率1/155＝0.645%。現行の0.5%制約では1件も許容できない。選定は0件にする0.99／0.99へ進み、同じ新dev・同じ係数でJA recallが68.33%→52.25%となる。品質目標すべてを満たす候補は105組中0であり、選ばれたことと採用可能であることは別である。

## 修正へ進むなら

1. **入力途中の評価を選定へ追加する。** 元文groupの分割を保ったdev traceで、記号あり／なし、取得不可／空、ローマ字別表記、追加／削除／全体入力の最終spanと表示を評価する。完成文とprefixの重み配分を明示し、記号増強でprefixが薄まらないようにする。testは調整に使わない。
2. **日英判定と変換区間を分ける。** 未完子音、読みだけの末尾、句読点で閉じた読みを区別する。採用済み区間が消えたことだけで、より広い漢字変換へ進む逆転を避ける。日本語のスコアだけでは漢字にすべきかを決めない。
3. **英単語候補の境界を安定させる。** 単一のViterbi pathのRAW端だけに依存しない、範囲を限定した辞書候補とローマ字妥当性の共同評価を検討する。現在のrawから再現できる条件にし、前表示の固定やmeeting固有の例外にしない。全substringへのZenzai呼出しは不要。
4. **空文脈の期待を明文化する。** 旧モデルの過大な加点を復元して回帰を通すのではなく、意味のない空文脈と取得不可の扱いを揃える方針を検討する。`made/no/to/name` の無条件例外は追加しない。

今回は調査の依頼なので、これらの修正は実装していない。閾値の一律緩和、テストの期待値変更、候補モデルの採用も行っていない。

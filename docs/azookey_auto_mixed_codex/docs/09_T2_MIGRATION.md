# 09. T2完了後の方針変更：曖昧語を文脈で判断する

## 1. 変更理由と範囲

初版の特徴量v1は未確定原文の各文字の前後8文字とn-gramを使う。したがって `I made` と `ashitamade` が同一の未確定入力内にある場合、LRでも区別を学べる。一方、直前に確定した `I ` と `明日` の後に同じ未確定原文 `made` を打つ場合、v1には両者の差が渡らない。また初版の孤立 `made/no/to/name` の無条件保留は、強い文脈があっても表示を妨げる。

T2のLR・Viterbi・保護規則を廃棄しない。T3で文脈付き特徴量v2を候補として加え、学習・凍結評価でv1と比較する。CRFや小型CNNへの切替はv2の評価後に必要性を判断する。ここに記す表示例は意図した契約であり、モデルの実測予測ではない。

## 2. 入力契約とプライバシー

判定器への入力を `(raw, leftCommittedContext?, contextAvailability, userOverrides, focusIdentity, revision)` とする。`raw` はT1の原文バッファで、span offsetは常にrawのUnicode scalar単位。左文脈は現在の入力欄から既存IMK経路で**読み取りが許され、取得できる場合のみ**直前の最大30 Unicode scalarsとする。値は学習の正解表示ではなく、実際に直前に確定した文字列。右側の確定済み本文は初期対象外とし、未入力の未来を見ない。取得できない、選択がある、フォーカスが変わった、またはセキュア入力中のときは `unavailable` とし、値を空文字に偽装しない。

先行文脈をログ・ディスク・学習データ収集へ記録しない。既存のZenzai向け文脈が取得可能でも、日英判定器が受け取ることは別のAPI変更である。XPCで渡す場合は既存の安全な取得・フォーカス拘束を確認し、別欄の文脈取得手段を増やさない。アプリ本文や他の入力欄をIMEが遡って書き換えない。文脈取得失敗時にもrawは完全保持する。

## 3. v2特徴量と互換性

既存 `AnchoredCharacterFeatures` v1および同梱 `feature_golden.json` は変更しない。v2は明示的な `feature_spec_version` を新設し、T2のSwift実装を確認して別テストとgoldenを作る。モデルartifactもv2として区別し、v1の係数へv2特徴を渡さない。v1のモデル・schema・fixtureもそのままテストに残す。

- rawの各文字位置について、v1の特徴をそのまま生成する。
- contextがavailableの場合、左文脈の末尾（上限30 scalars）、文字種、直前の空白／句読点／日本語文字、末尾の単語や短いn-gramを追加特徴にする。空白を含む `I ` と `明日` を区別しつつ、大きな固有名詞辞書を必須にしない。正確なキー符号化・境界規則はv2のPython参照とgoldenで固定する。
- contextがunavailableのときは明示的な欠損特徴を付ける。学習時にも同じ欠損状態を含める。文脈由来の文字をraw spanに加算したり、Viterbiのlabelとして出力したりしない。
- `raw` 全体は現在のprefixに限る。未確定バッファに続く未来の文字も、同じ文章の完成版もライブ判定には渡さない。
- 文脈・availability・focus・raw revisionが変わると、判定結果とZenzai候補の文脈依存cacheを無効化し、古い非同期応答は破棄する。文脈だけ変化した場合も既に利用者が採用した候補は無断変更しない。

保持したv1専用経路は、実装・評価の比較基準であり、v2未対応クライアントや文脈欠損での安全な経路にもできる。v2モデルの欠損状態を使うかv1へfallbackするかはdevデータで決め、試験時に経路を明示する。

## 4. 保留規則の更新

URL・メール・明確な識別子などのhard protectionは維持する。`made/no/to/name` の**綴りそのものをhard RAW maskや無条件保留リストにしない**。代わりに、データで校正したJA採用条件とRAW/JAの系列スコア差、ローマ字妥当性、利用可能な文脈、表示ヒステリシスを用いる。指標と閾値はdevで決め、平均文字pをspan全体の正解確率とは呼ばない。両解釈の根拠が弱ければrawで保留する。利用者の強制指定は安全上の保護規則と整合させる。

| 左の確定文脈 | raw | 期待する意図 | 試験上の扱い |
|---|---|---|---|
| `I ` | `made` | RAW | 明示意図の対照例 |
| `明日` | `made` | JA_ROMAN（まで） | 明示意図の対照例 |
| 取得不可 | `made` | AMBIGUOUS | 保留を許容 |
| なし | `ashitamade` | JA_ROMAN | 未確定raw内の文脈を使用 |
| `これは ` | `made in Japan` | RAW | 日本語文脈内の英語引用も学ぶ |

これらは注釈付きの設計例であり、そのとおりに学習・予測できた証拠ではない。確定文脈が「I」で空白が未確定rawの先頭にある実際のキー列も別途試験する。空白を消して仮想的な `Imade` を作らない。

## 5. データ、評価、受入れ

`span_record.schema.json` の任意 `left_context` / `context_available` を使用する（未指定の旧レコードはunavailableとして扱う）。rawとspansのoffset意味は変更しない。訓練例は同じ `raw` に異なる前文脈・意図を付けた対照ペア、英文中の英語、日本語中の英語、空白なし、URL、prefixを含める。注釈者が確定済み文脈と意図を確認する。文脈入手不可能なアプリを想定した欠損例も必須。

元の文章／テンプレート／対照ペア／全prefixは同じgroup_idにしてsplit前に束ねる。train/dev/calibration/testをまたがらせない。評価時もその打鍵時点で利用可能な左文脈とprefixだけを使用する。評価データの個人入力履歴を無断収集しない。

比較は同じ保護規則、学習分割、妥当性チェック、表示ヒステリシスで、(A) T2由来v1 LR＋Viterbi、(B) v2文脈付きLR＋Viterbiとする。context available/unavailable、曖昧語対照、英語in日本語、入力途中、アプリ種別ごとに英語span破壊率・JA recall・保留率・反転回数・p95遅延を出す。改善が有意でなくても安全閾値を下げて見かけのrecallだけ改善しない。CRF/CNNは同一条件の後続比較。

T3の受入れにはv1回帰維持、v2 Python/Swift parity、対照ペアのデータ契約、学習モデルカード、独立評価が必要。資料中の例題や人工重みだけで判別精度は確定できない。T4・T5では文脈の取得可能性、フォーカス変更、文脈変更中の遅延応答を確認し、T7の実機試験まで本番ONにしない。

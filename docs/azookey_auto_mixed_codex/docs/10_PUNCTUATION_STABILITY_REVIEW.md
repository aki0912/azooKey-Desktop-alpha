# 句読点による変換の変化：原因と修正方針

2026-09-24。調査対象HEAD：`362fa25b9dc66f5df4e096ced74bffda1747d2db`。この文書は検討結果であり、以下の修正・再学習は未実施。

## 結論

`asitanotennkiwoosiete.` が「明日の天気をおしえて。」になる原因は、句読点の偏った学習、文脈特徴の過大な影響、日英判定後に不要な変換境界を残す処理の組み合わせ。Zenzaiに同じ読み全体を渡した場合は「明日の天気を教えて」が返る。

表示履歴を固定したり、取得不可の文脈を空文字へ置き換えたりして症状を隠す方法は採らない。学習モデルの改善と、判定後の変換区間の整合を別の差分として評価する。

## 「時々」の条件

導入済みhelperへ独立セッションから固定例を一文字ずつ送った。各条件3回、計12回の結果は次のとおり。

| 最初の文字で渡す左文脈 | 後続文字で渡す左文脈 | 句点後の表示 |
|---|---|---|
| 取得不可 | 取得不可 | 明日の天気をおしえて。 |
| 取得不可 | 取得成功・空 | 明日の天気をおしえて。 |
| 取得成功・空 | 取得不可 | 明日の天気を教えて。 |
| 取得成功・空 | 取得成功・空 | 明日の天気を教えて。 |

同じ条件では毎回同じ結果になった。`AutoMixedServerSession` はcompositionを作る最初の入力で文脈を固定し、確定・取消後の次のcompositionで取得し直す。句点のキーだけが文脈を失った、という挙動ではない。

IMKクライアントは `string(from:actualRange:)` の戻り値を渡す。アプリやカーソル位置で取得不可・空・非空が変われば、このモデルでは結果が変わる。利用者の実際の再現操作でどの状態だったかは未収集であり、OS上の間欠性をすべて説明できたとは断定しない。本文・確定文脈の採取は行っていない。

## 三つの原因

### 1. 句点を日本語入力として学習していない

export manifestから学習元datasetのSHAを照合した。対象は `build/auto-mixed/expanded-700-se-20260924/dataset.json`、SHAは `b5bd29bbf48da0b2f57f3152be2eb85bb8b2e7df1c501fd8248d5009754a707e`。trainのみを集計し、凍結testの再採点・閾値選択はしていない。

train原文481件では、`.` の直前8文字にあるASCII英字のラベルはRAWが680位置、JA_ROMANが0位置。JA_ROMANの直後に `.` がある例も0件。ローマ字variant・prefix増強後も日本語の句点例は増えていない。`,` と `?` の同じ範囲にもJA_ROMANがなく、`。` と `、` はtrain原文にない。

実行時は日本語の句点もASCII `.` としてrawに残る。表示を「。」に変えるだけなので、モデルは英文で学習した記号を受け取る。これは表示と学習の契約を揃える必要がある問題。

実際の係数を分解すると、句点追加によって末尾eteの日本語スコアは約 `0.947 / 0.932 / 0.937` から `0.310 / 0.144 / 0.088` へ落ちる。記号のshape特徴の負係数と、文末EOS特徴の消失などが寄与している。これらはモデルの文字スコアで、校正済みの単語確率ではない。

### 2. 空の文脈が強い日本語の手掛かりになっている

v2は左文脈の特徴を、rawの全位置に同じ係数和として加える。取得不可はavailability特徴一つ、取得成功・空は最大30位置の文頭BOSとshapeなどになる。

現在のモデルでは空文脈から57個の特徴が有効になり、文脈の係数和が取得不可の約0.174から約5.296へ増える。校正後のlogit差は約+7.883で、今回の末尾スコアは空文脈なら句点後も約0.999 / 0.998 / 0.996になる。

train原文には空文脈が13件あるが、いずれも学習対象のRAW／JA_ROMAN英字位置がない。AMBIGUOUS等を除外する既存契約により、この条件を直接学習する正解がない。非空文脈も43原文・RAW80位置／JA43位置と少ない。空文脈の強い加点は、取得成功が正しく言語を知らせている証拠ではない。

取得不可と取得成功・空の区別自体は保持すべきだが、どちらにも意味のある左文脈がない場合、APIの成功だけで言語判断が跳ね上がる設計は見直す必要がある。

### 3. 英語判定を取り消した後も、その境界で漢字変換を切っている

現モデルのViterbi切替ペナルティは0。そのため末尾eteはそのままRAWへ分かれる。`JapanesePreferredSegmenter` はeteを英語として採用せず、japaneseKanaとして扱うが、前半のjapaneseRoman境界を引き継ぐ。

最終的に `[0,18)` の `asitanotennkiwoosi` だけをZenzaiへ渡し、`[18,21)` のeteは読み「えて」を表示する。`MixedSessionConverter` のjapaneseKana経路にはZenzai呼出しがない。全体が日本語扱いになった後も、古い日英境界が変換単位として残っている。

句点後の本文全体の日本語平均スコアは約0.8705で、既存hold値0.65を超える。全体をjapaneseRomanにする候補を作れるコードがあっても、前半anchorを優先して分断が残る。この例はhold閾値を少し下げれば済む問題ではない。

## 推奨する修正の順序と責任範囲

### A. 先に再現条件を回帰契約として固定する

現モデル、v1/v2 golden、既存テストは保存する。今回の固定例を不具合の回帰例として追加し、新たな独立評価データと区別する。文脈取得不可・取得成功空・日本語・英語・空白・改行、ローマ字別表記、句読点の追加／削除／再入力、逐次入力と全体入力を対照にする。

通常の英文 `I made it`、`go to school`、`this is my name`、apple、meeting混在、URL・ファイル名・小数、長音も同じ修正の回帰対象にする。既存の `asitan → 明日n` と、入力中の `asitanote → 明日のて` の期待値を理由なく変更しない。

### B. 日本語と英語の判定後に、変換単位を組み立てる

日英のラベル、漢字変換へ渡す読みの範囲、入力途中のかな表示を区別する。LRの日本語らしさを、そのまま「ここからは漢字変換を呼ばない」という語中境界に使わない。

最初の小さなコード差分の候補は、**区切りで閉じた、完成した日本語の読み**について、同じ日本語区間内のjapaneseRomanとjapaneseKanaを変換前にまとめる処理。日本語へ戻した末尾も全文脈を含む読みとして既存変換器へ渡す。英語として採用された区間、保護token、空白、利用者の明示選択をまたがず、標準ローマ字parserの妥当性を必須にする。原文やOSの確定状態は変えない。

入力途中の低信頼なかな末尾は暫定表示として維持し、区切りで読みが閉じたときの再変換とは区別する。これは「低信頼部分は常に読みだけ」という現在の処理からの仕様差分であり、区切り追加時には候補全体が再評価され得る。候補の自動OS確定は行わない。明示採用候補の維持・編集時の扱いを先にテストで定義する。

ただし、これだけでは修正完了にならない。対照調査では `osiete.` は全体がjapaneseKanaになり、`asitanote.` はnoteを英語として採用した。これらは結合対象にjapaneseRomanがない、または実際の英語判定が介在するため、単純な隣接span結合では直せない。学習・言語判定側の改善も必要。

### C. 実際のrawに合うデータを追加し、モデルを比較する

- 権利確認済みデータへ、日本語・英語・混在の各文に対するASCII句読点あり／なし／連続、句点後の英語、保護tokenへ成長する入力を追加する。画面上の「。」だけを学習rawに入れない。
- 明確な意図を持つ文について、文脈取得不可、実際に文頭である空文脈、短い非空文脈を揃える。文脈を落とす増強は可能だが、意図を文脈だけで定めた曖昧語のラベルをそのまま複製しない。
- 元文・対照ペアを同じgroupに束ね、split後に句読点・ローマ字variant・prefixを増強する。元文あたりの重みを保ち、今回の不具合例を独立testの精度改善として数えない。
- まず既存v2特徴量でデータ改善の効果を測る。続けて、空文脈の反復BOS加点を抑え、意味のない文脈をrawの証拠より優先しない特徴設計を別versionの候補として比較する。特徴量を変える場合はPython／Swift parity・schemaの更新を伴い、既存v2を上書きしない。
- 切替ペナルティと採用閾値はdevで再選択する。最終ラベル精度に加え、記号追加時の変換崩れと英語破壊を評価する。校正は別split、凍結testは選定後に評価する。

IMK側は、取得した範囲が要求範囲に対応すること、取得失敗を成功空と見なさないことを専用境界テストで確認する。現コードはactualRangeを検証せず、位置不明時に0を使う。これは確認が必要なリスクだが、今回実機でその分岐を通ったと確認したものではない。必要な実機診断は取得状態・長さ区分・composition世代だけに限定し、本文・文脈を記録しない。

## 単独では採用しない対処

| 対処 | 採用しない理由 |
|---|---|
| 最後の表示をそのまま固定 | 全体入力と逐次入力が食い違い、編集や英語・保護tokenへの成長を阻害する |
| 取得不可を空文字として扱う | 今回は症状が消えるが、誤った大きな日本語加点を利用するだけ |
| `.` を推論前に `。` に置換 | 学習分布とrawの問題を隠し、URL・小数等へ影響する。原文の表示規則とは分ける |
| hold閾値だけを下げる | 語中境界が残り、英語を誤変換する条件も広げる |
| Viterbiペナルティを例に合わせて上げる | 今回は1.2／2.4でもeteがRAWのまま。5なら結合するが、この1例だけで値を選べず、後続の採用gateも別に存在する |
| japaneseKanaをすべてjapaneseRomanへ変更 | 語中の分割を解消せず、入力途中のかな末尾の既存契約を壊す |
